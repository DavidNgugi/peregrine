# AGENTS.md — Rules for contributors (human and AI)

Peregrine is an open-source, cross-platform desktop application for media discovery, library management, torrent acquisition, and playback. It is built to be read by strangers: the code, the tests, and the documentation are the product as much as the binary is.

This file is the contract. It applies to every change, whether written by a person or generated by an agent. When a rule here conflicts with convenience, the rule wins; when a rule is genuinely wrong, change this file in the same pull request that proves it wrong.

Read order before touching code: this file → [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md) → the relevant [ADR](./docs/adr/) → [docs/TASKS.md](./docs/TASKS.md) for the task you are doing.

## 1. The rules, in one place

### Quality

- **R1 — Ship the whole change.** Tests, error handling, structured logging, and the doc updates that the change invalidates belong in the same pull request. There is no "tests in a follow-up".
- **R2 — No bloat.** No dependency, abstraction, configuration knob, file, or line that the current requirement does not need. Adding a dependency requires a stated reason in the pull request; adding a layer requires a reason the existing layer cannot serve.
- **R3 — No dead weight.** No commented-out code, no unused exports, no placeholder module, no speculative trait with one implementation and no planned second one, no feature flag left behind.
- **R4 — Every rule has a test.** If a behaviour matters enough to write down in a document, it has a test. Invariants in [docs/DATA_MODEL.md](./docs/DATA_MODEL.md) §3 map to named tests.
- **R5 — Edge cases are the job, not the stretch goal.** For every change, walk the checklist in §4 and write the tests that apply. "Happy path works" is not done.

### Architecture

- **R6 — Respect the dependency direction.** `domain` depends on nothing but `serde`, `jiff`, `ulid`, and `thiserror`. Adapters are leaves. `xtask check-arch` enforces the allowlist; do not add an edge without updating it deliberately.
- **R7 — The core owns state.** Business logic lives in Rust. The UI is a projection. If you are about to compute a rule in TypeScript, put it in `peregrine-domain` and expose it through IPC instead.
- **R8 — Ports and adapters.** Every external system sits behind a trait in the core and an adapter in a leaf crate. Third-party client types never escape the adapter that owns them.
- **R9 — No `unsafe`.** `#![forbid(unsafe_code)]` in every crate. If you believe you need an exception, open an ADR first. None is currently approved.
- **R10 — Commands are thin.** An IPC command parses, calls one service, and maps the result, in twenty lines or fewer. Anything slower than 100 ms becomes a job with progress events.
- **R11 — Blobs never cross IPC.** Images and media go over the asset protocol or the loopback HTTP server. IPC carries IDs, DTOs, and deltas.
- **R12 — Change the design in an ADR, not silently.** Reversing or bending a decision recorded in [docs/adr/](./docs/adr/) requires a new or superseding ADR in the same pull request.

### Testing

- **R13 — Test at the lowest layer that can express the behaviour.** Domain logic is unit and property tested. Adapters are tested against fixtures. UI tests assert interaction and focus, not business rules.
- **R14 — Deterministic and offline.** Tests never hit the network, never depend on wall-clock time, and never depend on the developer's machine. Time and IDs are injected. Provider HTTP is `wiremock` plus recorded fixtures. Torrents are a local seeder.
- **R15 — Property tests for parsers.** Release names, filenames, paths, torrent entries, subtitle timing, and quality scoring get `proptest` coverage, and the parsers get fuzz targets.
- **R16 — Performance budgets are enforced.** A change touching startup, grid rendering, search, IPC, or the scheduler runs the relevant bench, and a regression beyond 15% fails CI. Do not "fix" a budget by relaxing it in the same PR.

### Documentation

- **R17 — Document the why, once, in the right place.** Decisions go in ADRs. Structure goes in ARCHITECTURE. Behaviour goes in FLOWS. Data goes in DATA_MODEL. Work goes in TASKS. A user-facing answer goes in the README. Never duplicate an explanation in two files; link instead.
- **R18 — No unnecessary documentation.** A new markdown file must have a named audience and a reason the existing documents cannot carry. No per-module README sprawl, no changelog of your own work, no design note that restates the ADR, no generated doc that nobody opens.
- **R19 — Comments explain why, never what.** No section banners, no restating the signature, no narration of the diff. A comment earns its place by recording a non-obvious constraint, a workaround with its reason, or a hazard. Public items in library crates get a concise rustdoc line; nothing else is required.
- **R20 — Documentation is updated in the same change.** If your change makes a document wrong, the document is part of your diff.

### Security and safety

- **R21 — Follow [SECURITY.md](./SECURITY.md).** The threat catalogue is not advisory. Path handling goes through `PathGuard`; downloaded content is never opened with the system handler; secrets only in the keyring.
- **R22 — Destructive operations are confirmed and reversible.** Deletion requires an enumerated plan, uses the OS trash where available, and revalidates paths between planning and confirming.
- **R23 — Nothing leaves the machine unasked.** No analytics, no telemetry, no crash upload without an explicit opt-in and a scrubbed payload.
- **R24 — Respect providers.** Documented APIs only, conditional requests on every JSON endpoint (image CDNs that cannot revalidate are the documented exception), per-host rate limits that back off on `429`, no scraping, and no user-agent spoofing. An accurate, descriptive `User-Agent` that identifies the application is required identification, not spoofing — some providers block requests without one.
- **R25 — No copyleft in-process.** Copyleft tooling runs as a separate executable. See [ADR 0009](./docs/adr/0009-licensing-and-redistribution.md).

### Process

- **R26 — Work from a task ID.** Every change maps to a task in [docs/TASKS.md](./docs/TASKS.md) or a linked issue, and satisfies the Definition of Done in [docs/PLAN.md](./docs/PLAN.md) §8.
- **R27 — Conventional commits, signed-off.** `feat(scope):`, `fix(scope):`, `docs:`, `refactor:`, `test:`, `chore:`, `perf:`. Every commit carries a DCO sign-off.
- **R28 — Small pull requests.** One task, or a coherent slice of one. A pull request that cannot be reviewed in twenty minutes is too large.
- **R29 — Green gates, always.** Format, lint, arch check, migration check, type generation diff, tests, and budgets all pass. Do not merge with a skipped gate.
- **R30 — Do not expand scope.** If you find unrelated work, file it against the relevant epic; do not fix it here unless it is a security or data-loss defect.
- **R31 — Notifications are requested, configurable, and never the only signal.** The user is asked before we notify them and a denial is respected. Every notification is also an in-app centre entry with the same deep link, because OS delivery can fail silently and Windows can lose a click. Per-event enable and sound are user settings, critical events (security, disk) are exempt from quiet hours but never from OS focus modes, and no notification content may leak a path, a secret, or a magnet.
- **R32 — Agent access is scoped, consented, and audited.** The MCP interface is off by default and loopback-only; clients are paired and named; `read` is the only default scope; anything that spends bandwidth, disk, or privacy requires in-app confirmation naming the client; every call is audited. Content that originated outside the app — overviews, release names, file names — is returned to agents as labelled data and can never trigger a call by itself.
- **R33 — The server mode is LAN-only by default and read-only.** A listener that outlives the session gets per-device tokens, an explicit interface bind, an audit trail, and no delete or settings surface. WAN exposure is never a default and never a checkbox without a warning. Discovery must work without relying on multicast, because Wi-Fi makes SSDP unreliable.
- **R34 — Account scope is a parameter of every read, and gating fails closed.** Catalogue, library, episode, progress, watchlist, notification, and search reads all take an `AccountScope`; content outside it must be indistinguishable from content that does not exist. Unrated content is hidden from a restricted account. Capability checks belong in the services, never in the UI, so no path can let a child account acquire media. Never add a bypass, reset, or recovery route around the OS account gate.

## 2. Repository layout

```
apps/desktop/          Tauri shell (thin) + React app
  src/                 features/, app/, lib/
  src-tauri/           commands, capabilities, icons
crates/                one crate per module map entry in ARCHITECTURE §5
packages/              ui, theme, ipc-client, player-ui, i18n
assets/                branding, themes
docs/                  architecture, data model, flows, plan, tasks, adr, research
xtask/                 check-arch, check-migrations, gen-ipc, backlog-stats, release helpers
```

Where things go:

| You are adding | It goes in |
| --- | --- |
| A business rule, parser, scoring function, or state machine | `crates/peregrine-domain` |
| A table, query, or migration | `crates/peregrine-storage` |
| A new external service | A new adapter under `crates/peregrine-providers` (or the matching port crate) plus a registry entry |
| A user-visible screen | `apps/desktop/src/features/<feature>` |
| A reusable visual primitive | `packages/ui` |
| A colour, spacing, or motion value | `packages/theme` |
| A decision with alternatives | `docs/adr/` |
| A task | `docs/TASKS.md` under the right epic |

## 3. Commands

```bash
pnpm install                 # frontend workspace
cargo build --workspace      # backend
pnpm tauri dev               # run the app
cargo nextest run --workspace # backend tests
pnpm test                    # frontend unit tests
pnpm test:e2e                # Playwright flows
pnpm gallery                 # the component gallery, in a browser, in both themes
pnpm check-dead-deps         # unused frontend dependencies (needs pnpm install)
cargo xtask check-arch       # dependency rules
cargo xtask check-determinism # no wall clock or randomness outside an adapter crate
cargo xtask check-migrations # migration immutability
cargo xtask check-todos      # every deferral names a task or an issue
cargo xtask check-commands   # every IPC command fits the parse-call-map budget
cargo xtask check-offset     # no query pages with OFFSET; list reads use a cursor
cargo xtask check-dead-deps  # unused Rust dependencies (requires cargo-machete on PATH; the gate FAILS rather than skipping when it is absent)
cargo xtask check-docs       # broken links and mermaid block parity — NOT IMPLEMENTED YET (PG-E28-07); this line documents the intended command
cargo xtask check-theme      # theme schema and contrast gate
cargo xtask check-notices    # sidecar, Rust, and bundled-frontend attribution
cargo xtask icons --check    # platform icon sizes and formats — NOT IMPLEMENTED YET (PG-E22-02); this line documents the intended command
cargo xtask gen-ipc          # regenerate TS bindings
cargo xtask backlog-stats    # task and effort roll-up
cargo clippy --workspace -- -D warnings
pnpm lint && pnpm typecheck
```

Cargo keys its artifacts to the *shape* of the invocation and not only to the source: it unifies features over the members a command **selects**, so a narrower selection resolves a shared dependency differently and recompiles it. `cargo xtask gen-ipc` selects `peregrine-ipc` alone by design, and every `cargo test -p <member>` or `cargo check -p <member>` selects one member. A feature that only one member enables must therefore be declared at the workspace level in `Cargo.toml` rather than on the member that uses it — `tauri`'s `tray-icon` and `protocol-asset` are the ones that cost minutes, per PG-E0-20. Keep one shape for a whole session, and do not expect `cargo check` to rescue a loop on its own: an edit to `peregrine-domain` measured about 70 s through `cargo check` and about 70 s through `cargo build` (PG-E0-20), because the cost is front-end analysis across the eight crates that depend on it rather than codegen or linking. What costs minutes is changing shape.

**Everything is built and tested in the development profile, and that is the profile this work is judged in.** `cargo test`, `cargo clippy`, and `cargo xtask` all default to `dev`, `target/debug` holds the artifacts being iterated on, and no gate needs `--release`: a release build is a packaging step, not a verification step, so nothing here reaches for one to make a run faster or a gate pass.

**Run the workspace shape once, at the end of a change, and read its result.** Rebuilding is not a way to make progress and re-running the suite after every edit is not verification — it is the same answer bought again, at the price of the whole front end. While editing, run the one test whose behaviour you just changed, by name; when the change is complete, run the commands in the list above and report what they said. A gate that has not been run is reported as not run, which is a different and more useful statement than a rebuild nobody asked for.

**A bare `cargo` command does not build the shell.** `default-members` in the root `Cargo.toml` lists every member except `apps/desktop/src-tauri`, because the Tauri shell's link is the most expensive single step in the tree and nothing that iterates on the core needs it: bare `cargo build`, `cargo test`, and `cargo clippy` cover the crates, while `cargo build -p peregrine-desktop` (or `pnpm tauri dev`) still builds the shell when the shell is what you are changing. This narrows no gate — every command above spells `--workspace` or selects a member.

**And measure what is left, because it is not all compilation.** On macOS arm64 after this change: a bare `cargo test` that covers the sixteen crates and their seventeen test binaries took **8 m 31 s from cold and 2 m 13 s warm, of which `user` was 28 s and `sys` 1 m 44 s** — the steady-state cost is *linking and debug-info I/O*, not analysis. A `cargo test -p peregrine-app` in the same tree took 1 m 17 s with `user` + `sys` of 27 s, and the difference between those two numbers is the point: **most of that wall time was cargo reshuffling artifacts because the invocation shape changed between the two runs**, which is PG-E0-20's finding and the reason this file says to keep one shape for a session. So: pick `-p <member>` for the crate being edited and stay in it while iterating, then pay for the documented `--workspace` shape once at the end. Unmeasured and deliberately not changed here: whether `split-debuginfo = "off"` in `[profile.dev]` would cut that I/O further — it would cost the symbols a dev panic's backtrace needs, and no measurement in this tree justifies that yet.

Enable the local pre-commit hooks once per clone. They run formatting, the
architecture check, the migration check, and lint on staged files, scoped to what
the commit touches:

```bash
git config core.hooksPath .githooks
```

Any new recurring command is added to `xtask` — or, for the frontend, to `package.json` scripts — and documented here in the same pull request.

## 4. Edge case checklist

Walk this list for every change and write the tests that apply. It is deliberately mechanical; the failures this project must never ship are on it.

| Category | Ask yourself |
| --- | --- |
| Empty | What happens with zero items, zero results, an empty string, an empty file, an empty torrent? |
| Single | Does exactly-one behave differently from many? |
| Boundary | Off-by-one at the first and last item, at a 0% and 100% progress, at a size exactly equal to a cap? |
| Threshold | Values just below, exactly at, and just above every configured limit and policy cutoff? |
| Malformed | Truncated, wrong type, wrong encoding, extra fields, missing required fields, HTML instead of JSON? |
| Hostile | Traversal, absolute path, symlink, unicode spoofing, enormous value, deeply nested structure, decompression bomb? |
| Duplicate | Same input twice, two jobs for the same target, the same file in two roots, a repeated request after a retry? |
| Concurrent | Two writers, two scans, a scan during playback, a delete during a download, cancellation at every await point? |
| Interrupted | Killed mid-write, mid-migration, mid-download, mid-transcode; power loss between commit and fsync? |
| Missing | File absent, root unreachable, device gone, provider down, keyring unavailable, binary missing? |
| Full | Disk full, cache cap reached, connection limit reached, queue at maximum? |
| Slow | Timeout, stall, partial response, network flap, 429 with `Retry-After`? |
| Permissions | Path not writable, permission revoked mid-session, keyring locked, OS denied the request? |
| Platform | Does the behaviour differ on macOS, Windows, X11, Wayland, and at 125%/150%/200% scaling? |
| Locale | Non-ASCII titles, right-to-left text, 1.4× text expansion, locale-aware sorting and dates? |
| Time | DST transition, clock skew, a month-old cache, an item scheduled in the past? |
| Reversal | Undo and redo, mark watched then unwatched, remove then re-add, cancel then retry? |

## 5. Code standards

### Rust

- Errors: `thiserror` per crate with typed variants; `anyhow` only at the application boundary where context is added. No `unwrap` or `expect` outside tests, startup assertions, and provably-infallible cases with a comment.
- Visibility: crates expose the smallest surface that callers need; `pub(crate)` is the default inside a crate.
- Async: never hold a database transaction across an `.await` on a network call; never block the runtime — use `spawn_blocking` for hashing, image decode, and filesystem walks.
- Naming: domain language, not implementation language. `WatchProgress`, not `ProgressRow`. Types that mirror database tables end in nothing; row mappers are internal and clearly named.
- Newtypes over primitives for anything with a unit or an invariant: `Bytes`, `Millis`, `Percent`, `SafePath`, `ImdbId`.
- Iterators over index loops; `Option`/`Result` combinators over nested `match` where it reads better, and explicit `match` where it does not.
- Every module has tests next to it (`#[cfg(test)]`), and cross-crate behaviour has an integration test under `tests/`.
- A failing property test writes its seed under `proptest-regressions/`. **Commit that file** — it is what makes the failure permanent, and proptest's own guidance is to add them to source control. It is not build output, and deleting it throws away the regression. Review it rather than sweeping it in with `git add -A`, because the seed is only meaningful next to the test that produced it.

### TypeScript and React

- `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. No `any`; `unknown` plus a narrowing function at boundaries.
- No business rules. If you are computing eligibility, availability, scoring, or policy, it belongs in Rust.
- Colocate by feature: `features/<feature>/{components,hooks,queries}`. A feature never imports another feature's internals.
- Hooks first: a component that needs three `useEffect`s for data is a data-layer bug, not a component bug.
- Keys are stable domain IDs, never indices.
- Animations touch `transform` and `opacity` only, and every non-essential animation has a reduced-motion branch.
- Every interactive element is reachable and operable by keyboard, with a visible focus state per platform convention.
- No `dangerouslySetInnerHTML`, no `eval`, no remote script, no inline script.

### SQL

- Migrations are append-only, numbered, and never edited after merge.
- Every hot query is keyset-paginated; `OFFSET` is not used.
- Indexes are added with the query they serve, and the query's cost is stated in the pull request.
- Constraints do the guarding that the database can do: `CHECK`, `UNIQUE`, partial unique indices, foreign keys with explicit cascade behaviour.

## 6. Performance discipline

| Hot path | Budget | Gate |
| --- | --- | --- |
| Cold start to interactive | ≤ 1200 ms (Apple silicon), ≤ 2000 ms (Windows mid-tier) | CI startup trace |
| Discover first paint from cache | ≤ 100 ms | E2E assertion |
| Browse grid scroll | ≥ 60 fps at 5 000 items | Frame-time histogram gate |
| Search keystroke to results | ≤ 16 ms p50, ≤ 50 ms p95 | Criterion bench |
| IPC response | ≤ 64 KB, progress ≤ 4 Hz per job | Contract test |
| Idle memory | ≤ 250 MB RSS excluding sidecars | Soak test |

Rules: measure before optimizing and after; never trade correctness for a micro-optimization; never add an animation or effect that requires layout during interaction.

## 7. Working with agents

If you are an AI agent contributing to this repository:

1. Read this file, then [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md), then the ADR that governs your area, then the task you are implementing. Do not start from the code.
2. Identify the task ID from [docs/TASKS.md](./docs/TASKS.md). If the work is not in the backlog, add it before implementing it.
3. Make the smallest change that satisfies the task's acceptance criteria, with the tests the task implies.
4. Run the gates in §3 before reporting completion. Report failures honestly rather than describing intent.
5. Update the documents your change invalidates in the same change. Do not add new documentation files beyond R18.
6. Never weaken a test, a budget, a security control, or an invariant to make a change pass. If a control is genuinely wrong, propose an ADR.
7. Never invent a dependency version, a provider endpoint, an API shape, or a benchmark number. Verify it or mark it unverified.
8. When a task is larger than five ideal days, break it down before writing code.
9. Leave the repository in a state where the next contributor needs no context from you beyond the documents.

### Output contract

When the reply itself is the deliverable — a snippet, a patch, an answer to "write me X" — the reply is code, not commentary about code.

- **Strict syntax.** Return only executable code, in one fenced block per language, that runs as written. No inline comments, docstrings, or type-hint explanations unless they were asked for. No template filler where a real symbol belongs.
- **No preamble.** No "Here is the code", no restating the request, no markdown introduction, no running narration of the diff. The enforcement phrases are "No explanation needed" and "Concise code output only"; under them the whole reply is the code block.
- **Prose, if any, comes after.** A prerequisite, tradeoff, or hazard the code cannot show goes in one short block after the code, never before it and never between blocks.
- **Why, never what.** This is R19 applied to chat: a comment earns its place by recording a constraint, a workaround's reason, or a hazard, and nothing else. Committed files follow R19 in full — public library items keep their concise rustdoc line.
- **Senior-engineer stance.** Write production-ready, low-entropy code and let it speak. Prefer the smallest correct change over a demonstration, and delete anything that does not change behaviour.
- **Deterministic.** No invented API, dependency version, provider endpoint, or benchmark number, and no variation for its own sake. An unverified value is labelled as one rather than guessed.

## 8. Review checklist

A reviewer confirms, in this order:

1. The change maps to a task ID and satisfies its acceptance criteria.
2. The architecture rules hold (layering, thin commands, no business logic in the UI, no `unsafe`).
3. Tests exist for the edge cases in §4 that apply, and they would fail if the logic broke.
4. Errors are structured, user-facing messages say what to do, and logs are redacted and sufficient to diagnose without a debugger.
5. Performance impact is measured if a hot path is touched.
6. Security controls from [SECURITY.md](./SECURITY.md) are intact; no new trust in untrusted input.
7. Documentation that the change invalidates is updated, and no unnecessary documentation was added.
8. No dead code, no new dependency without a reason, no scope creep, no weakened gate.
